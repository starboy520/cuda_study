# CUDA 工程师面试 14 天突击计划：设计说明

## 1. 目标

新增一份可直接执行的学习文档 `docs/CUDA工程师面试_14天突击计划.md`，将仓库中已经学过的 CUDA 内容、尚未完成的深水区内容、独立编码训练和面试训练组织成一条 14 天闭环路线。

目标不是继续扩大知识面，而是在每天约 8 小时的条件下，把现有知识转换成四种面试能力：

1. 闭卷解释 CUDA 概念；
2. 独立写出常见 kernel；
3. 使用正确性、计时、ncu 和 PTX/SASS 建立性能证据；
4. 在面试中清楚讲述项目、优化过程和取舍。

## 2. 用户与前置基础

文档面向本仓库当前学习者。默认已经学习或实践过：

- CUDA 执行模型、内存层次、同步和错误检查；
- coalescing、shared memory、bank conflict、向量化；
- atomic、warp 原语、reduction、scan、histogram；
- stream、pinned memory 和传输计算重叠；
- GEMM 从 naive 到 shared/register tiling、向量化和双缓冲；
- Roofline、Nsight Compute、Compute Sanitizer；
- WMMA、Attention、Online Softmax 和教学版 FlashAttention。

当前主要缺口是 PTX/SASS、warp MMA、调度与 stall、工业级异步流水，以及把零散实验整理成可验证的作品和面试表达。

## 3. 采用方案

采用“面试闭环型”结构：

| 阶段 | 时间 | 目标 |
|---|---:|---|
| 深水区补齐 | Day 1～7 | PTX/SASS、寄存器、调度、MMA、异步流水与 Hopper |
| 独立实现与项目收口 | Day 8～11 | 闭卷手写、补齐推理练习、整理 A100 旗舰案例 |
| 面试转换 | Day 12～14 | 八股、限时编码、性能诊断、项目讲解和模拟面试 |

不采用“14 天全部投入底层指令”的方案，因为会挤压独立编码和面试表达；也不采用“主要打磨作品”的方案，因为 PTX/SASS 与调度器仍是当前最明显的知识缺口。

## 4. 每日结构

每天以约 8 小时为上限，默认分配为：

- 2 小时：概念学习；
- 3 小时：代码和实验；
- 1.5 小时：整理正确性、性能和指令证据；
- 1.5 小时：闭卷复述、限时手写和纠错。

正式文档为每天提供：

1. 当日目标和完成优先级；
2. 仓库内必读资料链接；
3. 必做实验的逐步操作；
4. 必须保留的输出物；
5. 闭卷验收题；
6. 未通过时的补救方法；
7. 可直接用于面试的口述主题。

## 5. 三阶段内容

### 5.1 Day 1～7：深水区

学习顺序为：

```text
CUDA C++ → PTX → SASS
→ 寄存器、spill 与宽访存取证
→ scheduler、scoreboard、eligible warp 与 stall
→ fragment、ldmatrix 与 mma.sync
→ cp.async group 和多 stage 流水
→ Hopper 的 TMA、WGMMA、Cluster/DSM 与 warp specialization
→ 对一个现有 A100 kernel 完成综合证据链分析
```

深水区以 `docs/CUDA深水区_PTX_SASS_MMA_异步流水与Hopper.md` 为主教材。Ampere/A100 内容要求动手验证；Hopper 内容只要求正确理解、架构对比和口述，不要求提供无法在 A100 上获得的性能数据。

`mma.sync` 要完成最小正确性实验并找到相应机器指令，但 14 天内不要求达到 CUTLASS 生产内核水平。

### 5.2 Day 8～11：独立实现与作品

独立手写训练至少覆盖：

- reduction；
- shared-memory transpose；
- 数值稳定 softmax；
- tiled GEMM；
- warp-per-row GEMV；
- RMSNorm；
- 根据时间完成一个融合或推理专项 kernel。

仓库中的 CUDA Graph、Fused RMSNorm 和 Dequant GEMV 练习纳入这一阶段。代码必须经过 CPU/reference 对拍、边界 shape、重复运行和适用的 Compute Sanitizer 检查。

旗舰案例优先从现有 A100 GEMM 或 Attention 实验中选择，不重新发明无关项目。最终案例需要包含：

- 问题和硬件环境；
- baseline；
- 优化阶梯；
- 正确性与边界验证；
- 可靠计时和吞吐指标；
- Roofline 或瓶颈判断；
- ncu 与 PTX/SASS 证据；
- 至少一次失败尝试及原因；
- 与 cuBLAS、CUTLASS 或理论上限的差距；
- 5 分钟和 10 分钟两个项目讲解版本。

### 5.3 Day 12～14：面试转换

训练内容包括：

- CUDA 高频概念题闭卷回答；
- 常见 kernel 限时手写；
- 给定 ncu 症状的性能诊断；
- 项目逐层追问；
- A100 与 Hopper 架构对比；
- 至少两轮完整模拟面试。

正式文档将链接现有面试题库，但不会要求机械背完整答案。回答模板统一采用“先结论、再适用边界、最后给项目证据”。

## 6. 验收机制

每天必须留下四类输出：

1. 概念输出：闭卷解释当天主题；
2. 代码输出：完成指定 TODO 或从空白处写出核心逻辑；
3. 证据输出：正确性、计时、资源、ncu 或 SASS 中适合当天主题的证据；
4. 面试输出：一段 2～5 分钟的可复述回答。

“阅读完成”不作为验收结果。

某天未通过时，第二天先安排最多 90 分钟补考；再次未通过则记录为薄弱项，在 Day 12 集中回补，避免一个难点拖垮全部 14 天计划。

最终验收要求：

- 能沿数据流阅读普通 kernel 的关键 PTX/SASS；
- 能解释寄存器、spill、occupancy、ILP/TLP 和 scoreboard 的关系；
- 能解释 `ldmatrix`、`mma.sync`、`cp.async` 的职责和边界；
- 能独立写出六个核心 kernel，并正确处理主要边界；
- 完成三项推理练习或明确记录未完成项；
- 完成一个 A100 旗舰性能案例；
- 能在 10 分钟内讲清项目；
- 能完成一轮 45 分钟 CUDA 技术模拟面试；
- 能正确比较 Ampere 与 Hopper 的关键执行和数据搬运机制。

## 7. 优先级与取舍

正式文档对任务使用三个等级：

- 必须完成：直接决定当前面试通过率，不得用扩展阅读替代；
- 尽量完成：用于区分普通候选人与有性能深度的候选人；
- 时间不足可跳过：短期内不会阻止参加初级或中初级 CUDA 面试。

优先保证正确性、独立实现、证据链和表达。时间紧张时，先缩减 Hopper 细节、复杂 fragment 映射和额外 kernel 数量，不取消每日验收和旗舰案例。

## 8. 文档落地与仓库边界

正式输出文件为：

`docs/CUDA工程师面试_14天突击计划.md`

文档通过相对链接复用仓库现有教材、代码、笔记和性能记录，避免复制大段已有内容。计划编写阶段不修改现有教材和 CUDA 源码。

文档末尾包含：

- 当前能力画像与目标岗位匹配表；
- 投递前检查表；
- 旗舰项目介绍模板；
- 常见追问清单；
- 第 14 天后仍有薄弱项时的补救路径。

工作区当前存在用户未提交的删除和新增文件。创建计划时只操作本次新增的设计、计划和最终学习文档，不整理、暂存或覆盖其他改动。

## 9. 完成标准

最终 Markdown 必须满足：

- 14 天均有明确时间分配、任务、输出物和验收条件；
- 所有引用的仓库文件路径存在，链接方向正确；
- 明确区分 A100 可实测内容与 Hopper 概念内容；
- 不把阅读或背诵当作唯一任务；
- 至少提供一套未按期完成时的压缩策略；
- 用户能够不依赖额外口头说明，直接按文档开始突击。
